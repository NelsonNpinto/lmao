## Decisions

- **D1. Study window.** Default delivery days are 2026-01-02 to 2026-02-01 inclusive, i.e. the half-open window `[2026-01-02, 2026-02-02)`. These are the days whose purchase decision (on D-1) falls in January 2026. A setting switches to calendar-January delivery.
- **D2. Cutoff.** Default 09:00 UK local time on D-1, converted to UTC per day so it stays correct across BST. A vintage with `publishTime == cutoff` counts as available (`<=`).
- **D3. Hourly forecast to half-hours.** Each hourly WINDFOR value at `HH:00` applies as a step to `HH:00` and `HH:30`. Metrics are computed on half-hours (1,488 pairs for the default window). The UI and docs label the effective number of independent forecast values (744). Nothing is interpolated.
- **D4. Chunking.** Requests use 7-day slices, concurrency 3, a 30 s timeout, and exponential backoff with jitter on 429/5xx. Forecast publish windows start 4 days before the first delivery day.
- **D5. Storage.** Postgres in production, SQLite locally and in tests, using the same SQLAlchemy models. Every forecast vintage is stored.
- **D6. Bias is reported, not fixed.** The pilot measures the public forecast as published. Bias correction is roadmap step 1.
- **D7. Frontend toolchain.** React 19 instead of 18: it is current, and every planned library supports it. Vite 8, Tailwind 4, TypeScript pinned to 5.9 because `openapi-typescript` needs `typescript@^5`. Vitest 4.1. **npm ≥ 11 is required**: npm 10.9 crashes while resolving the dependency tree.
- **D8. Python 3.12** via uv, as the brief specifies, even though the host has 3.13.
- **D9. Scope for now.** Git, CI and hosting are deferred at the user's request. Work concentrates on running the app locally. Hosting will be Vercel or Render (to be decided), so the backend stays host-agnostic.

- **D10. Seed window.** Ingest covers delivery days `[2026-01-01, 2026-02-02)`, so both the default study window (D1) and calendar-January delivery work from one load. Actuals start one day earlier (2025-12-31) for the persistence baseline. Forecast vintages start 4 days before the first delivery day (published from 2025-12-28), which is more than the brief's 3-day minimum. Result: 1,584 actual half-hours (33 × 48), 21,024 forecast rows, 288 vintages, 0 rejected, 0 incomplete days. A refresh run takes about 2 s.
- **D11. Idempotent upserts.** Actuals are keyed `(start_time, fuel_type)` and update only when Elexon republishes with a later `publish_time`; each update increments `revision_count` (Break #2). Forecasts are keyed `(start_time, publish_time)` and update only if the value changed. Both use `INSERT … ON CONFLICT … RETURNING`, so `rows_upserted` counts real changes: an identical re-run reports 0 (tested).
- **D12. `lead_time_h` is a stored column**, computed at ingest, not a DB-generated column, because SQLite and Postgres differ on interval arithmetic.
- **D13. Run status semantics.** `failed` means a contract violation (missing or renamed field) or every slice failed. `partial` means some slice failed, a past day has fewer than its expected periods (48, or 46/50 on clock-change days), or a past forecast slice returned no vintages. `succeeded` means none of those. Quality counters (null, negative, duplicate, non-wind, resolution) are stored on the run.
- **D14. Startup seed.** On boot, if no ingest run has ever completed (`succeeded` or `partial`), the app starts a background seed in `read_through` mode: committed raw cache first, Elexon only for missing slices. An interrupted seed is marked `failed` on the next boot and retried, rather than leaving a half-loaded DB looking complete. Found the hard way: the dev server's reload interrupted the first real seed.
- **D15. Raw cache is committed** (`data/raw`, 160 KB gzipped for the whole window), so `docker compose up` and the demo work with Elexon down. `POST /api/v1/ingest/runs` defaults to `refresh` (always calls Elexon) and needs `X-Admin-Token`. A concurrent request gets 409 with the running job.
- **D16. `data_version`** is an in-process counter, bumped when a run changes rows. Analytics caches (Phase 3) key on it.

- **D17. Aligned frame is a left join onto the delivery grid**, not an inner join. Every half-hour of the window appears with `has_actual` / `has_forecast` flags, so gaps are counted, never silently dropped. Metrics use rows where both exist.
- **D18. Margin sign convention.** `e = forecast − actual`. The desk plans on `forecast − margin`. A half-hour is covered when `e ≤ margin`. The flat P90 margin is the 0.9 quantile of `e`, which can be negative if the forecast under-forecasts; it is not floored at 0.
- **D19. Walk-forward history = days fully published before the cutoff.** At a 09:00 D-1 cutoff, D-1's actuals are still arriving, so training uses D-2 and earlier. Expanding window, minimum 7 history days (8 of 31 January days skipped). Stricter than "days before D", and the honest version.
- **D20. Conditional margin = forecast-level terciles**, empirical quantile per bin, falling back to flat below 30 training half-hours. Chosen over quantile regression because it is transparent, needs no extra dependencies, and plugs into the same walk-forward harness. Lead-time conditioning is not used yet: with a fixed cutoff it is confounded with hour of day.
- **D21. Confidence intervals = day-block bootstrap** (1,000 resamples of whole days, fixed seed 0, percentile method, skipped below 5 days). Resampling half-hours would ignore autocorrelation and make intervals far too narrow.
- **D22. Revision signal** compares vintages published in the 48 h up to the cutoff on the hours they all cover. A first version required "full-day" vintages and silently excluded every D-2 vintage (they stop at 21:00 UTC on D), which gave a meaningless 0.04 MW range. Caught on real data and fixed; V6 corrected at the same time.
- **D23. Phase 2 findings (09:00 cutoff, January 2026).** MAE 2,042 MW [1,642–2,485]; bias +1,748 MW [1,234–2,291]; P90 margin 4,140 MW; skill vs persistence 0.49. Moving to an 11:00 cutoff improves MAE by only 26 MW. Walk-forward P90 coverage is 85.2 %, not 90 %. The conditional margin matches that coverage with 16 % less over-procurement. Windy days carry +2.5 GW bias against +1.1 GW on calm days. Full table in `docs/METHODOLOGY.md` §7, reproduced independently with plain pandas (§8).

- **D24. Whole dataset in memory per data version.** About 23k rows. The analysis service loads it once per data version and memoises every derived result by `(version, window, cutoff, …)` in an LRU. CPU work runs in a worker thread.
- **D25. Window clamping.** Requested windows are trimmed to days that have actuals, with `meta.clamped = true` and a note. A window with no data at all returns 200 with empty arrays and `completeness = 0`, never 404.
- **D26. Series resolution.** `30m` by default. If a window would exceed 5,000 points, the server coarsens to `1h` and then `1d`, and says so in `meta.notes`. Aggregation is a plain mean, and any bucket missing a half-hour is null. Mean aggregation was chosen over LTTB because LTTB drops points and can hide gaps, and energy desks reason in averages.
- **D27. Band = window error quantiles.** The P10–P90 band on the forecast is `forecast − P90(e)` to `forecast − P10(e)` over the window, labelled `in_sample_window`. The calibration endpoint reports how honest that band is, both in-sample and walk-forward.
- **D28. One history rule everywhere.** The dashboard plan, replay and walk-forward backtest all train on days in the analysis window whose actuals were complete before the cutoff. Replay first used all data from the first ingested day and disagreed with the plan (13 vs 12 history days, 4,835 vs 4,568 MW for 15 Jan); fixed and covered by tests.
- **D29. HTTP caching.** Weak ETag = `(data_version, full URL)` on analytics GETs, plus a 64 MB byte-bounded response cache. A matching `If-None-Match` returns 304. Gzip is applied above 1 KB (series: 333 KB → 29 KB). CSV exports up to 50k rows are built in one go and cached; larger ones stream.
- **D30. Latency measurement.** p95 under 300 ms holds with a large margin (table in the README). An asyncio httpx benchmark first suggested 300–600 ms at 10 concurrent requests; ApacheBench and sequential timing showed the client itself was the bottleneck. Published numbers are from ApacheBench.
- **D31. Not built yet:** rate limiting on the ingest endpoint (it is admin-token protected and single-flight), the PDF brief, and the LLM endpoints. Planned for later phases.

- **D32. Frontend stack as built.** React 19, React Router 8, TanStack Query 5, Zustand (theme and toasts only), Recharts 3, Motion, Tailwind 4, zod, and openapi-fetch on the generated types. Server state lives only in TanStack Query. View state (window, cutoff, day, policy) lives only in the URL.
- **D33. Validated chart palette.** Actual = aqua, forecast = yellow, error = red/blue, chosen with the dataviz palette validator against each mode's surface (lightness band, chroma floor, CVD ΔE, normal-vision ΔE, contrast). Light: `#00897b` / `#b7791f`, `#c2410c` / `#0369a1`. Dark: `#199e70` / `#c98500`, `#e66767` / `#3987e5`. The first picks failed: the dark-mode colours were too light, and the light teal fell below the chroma floor. Error colours never share a plot with the forecast line. Every series also has a text legend and a table view, so identity is never carried by colour alone.
- **D34. Chart colours are resolved values, not `var(--…)`.** SVG presentation attributes, which Recharts writes, do not resolve CSS custom properties, so the first chart drew invisible lines. `useChartColors` reads the tokens and re-reads them on theme or OS-scheme change.
- **D35. `Cache-Control: no-cache` + build-salted ETag.** The first version sent `max-age=60`. When a response shape changed (vintage points went from tuples to objects), the browser kept serving the old JSON and broke the sparklines. Now every request revalidates (a 304 is cheap), and a new server process never matches an old ETag.
- **D36. Vintage points are objects.** `{start_time, forecast_mw}` instead of `[time, mw]` tuples, because openapi-typescript turned tuples into `(string|number)[][]`. The contract is now typed honestly end to end.
- **D37. Dashboard data flow.** The day chart filters the cached window series rather than fetching one day, so the P10–P90 band reflects the window's error distribution and day-to-day navigation is instant. The day's KPIs use the procurement plan (walk-forward margin) and the day's vintage list (forecast age).
- **D38. Accessibility in the chart.** The chart wrapper is the single focus stop. Arrow keys, Home and End step through a live readout (period, forecast, actual, error, lead). Recharts' own accessibility layer is off, to avoid a duplicate tab stop. A "Show as table" toggle gives the data-table fallback.
- **D39. Bundle split** into react, charts, motion and vendor chunks. App code is 35 KB (11 KB gzipped); the largest vendor chunk is 344 KB (101 KB gzipped).

- **D40. Cutoff sweep precomputed.** Startup warms all 24 hourly cutoffs (alignment, metrics, margin backtests), and the sweep endpoint computes rows concurrently. The 24-cutoff sweep answers in 11–26 ms, so the explorer's slider can redraw every chart from local data at 60 fps (`useDeferredValue`) and only commits the cutoff to the URL on release.
- **D41. Heatmap and scatter are computed client-side** from the cached window series (1,488 points), not from new endpoints: no extra round trips, and every view of the same window agrees by construction.
- **D42. Fan chart = emphasis, not 20 categorical colours.** The vintage used is orange, earlier vintages gray with opacity rising with recency, after-cutoff vintages dashed, and the actual aqua. The dataviz rules forbid more than about 8 categorical hues, and the story is "which one did we use and how did they converge".
- **D43. Admin token in the UI.** "Refresh from Elexon" asks for the admin token and keeps it in `sessionStorage` (this tab only). The API still enforces it: 401 without it, 409 while a run is active.
- **D44. Day explorer and command bar share one day.** The route's date wins on arrival and is written to `?day`; afterwards the command bar's picker drives the route. This fixed the command bar showing a different day from the page.
- **D45. Command palette is in-house** (about 150 lines: pages, days in any of "2026-01-15" / "15 Jan" / "15/01", cutoffs, theme). A library would have added weight for a list of about 20 items.
- **D46. Playwright smoke** (5 tests, about 10 s) runs against the real stack in `Asia/Kolkata`: cutoff change → vintage and KPI change, keyboard day stepping, malformed link recovery, every page renders without errors, and the phone layout has no horizontal scroll.

- **D47. Docker images.** The backend image is multi-stage: uv build stage → `python:3.12-slim`, non-root, healthcheck on `/ready`. Its build context is the repo root so it can bake in `data/raw`. The frontend image builds the bundle and serves it from nginx with SPA fallback, gzip, immutable `/assets`, and a same-origin `/api` proxy, so the container setup needs no CORS. Compose waits for health: Postgres, then the API, then the UI.
- **D48. Docker verified.** At first Docker Desktop on the development machine was broken (missing CLI folder), so Postgres was verified with an embedded server (`pgserver`): all 119 tests plus the seed, rerun and report gave results identical to SQLite. `TEST_DATABASE_URL` runs the suite on Postgres with a clean schema per test. Once Docker was repaired, `docker compose up --build` was verified from a clean volume:
  - db, backend and frontend all healthy in 28 s, with the first-boot seed from the committed cache taking 1.5 s and no errors in the logs;
  - Postgres holds 1,584 actuals and 21,024 forecasts at migration 0001, and the API gives MAE 2,042 / bias 1,748 / P90 4,140 through the nginx proxy;
  - SPA routes, gzip, ETags, `no-cache` on the API, immutable assets, the snapshot manifest, CSV export (1,488 rows), 401 without the token, and the backend running as non-root;
  - a live refresh from inside the container fetched all 11 slices from Elexon and changed 0 rows.

  Image sizes: API 393 MB, UI 54 MB.
- **D49. Static snapshot fallback** (Break #20). `python -m app.cli snapshot` saves the 169 API responses the UI requests for the default view: 3.3 MB, about 390 KB gzipped. The client's fetch is swapped for a snapshot lookup when the API health probe fails within 8 s, or always with `VITE_STATIC_SNAPSHOT=true`. Lookup keys are `path?sorted-decoded-params`, generated identically in Python and TypeScript (tested on both sides). Requests outside the snapshot return 404 with a clear message, and writes return 503.
- **D50. Verified the static build with no backend.** A production `VITE_STATIC_SNAPSHOT=true` build, served by a plain static server with SPA fallback, rendered the Day explorer with 0 API calls. A Playwright test blocks `/api/v1/*` and expects the snapshot banner, the dashboard numbers, and an honest "not in the offline snapshot" for another cutoff. Lesson: the Playwright glob `**/api/**` also blocked Vite's `/src/lib/api/` modules; the route now matches `/api/v1/` only.
- **D51. Day margin vs window margin.** The dashboard now labels both: "For this day: hold back 3,989 MW, learned from the 18 days known before the cutoff" (walk-forward) above "Across the window: … 4,140 MW" (fitted on the whole window). Previously the KPI and the sentence showed different numbers without explanation.
- **D52. Screenshots are generated** by a Playwright script (`make screenshots`, reduced motion, fixed 1440 × 960 viewport) so the README images can be rebuilt after UI changes rather than captured by hand.

- **D53. uv in Docker.** `ghcr.io/astral-sh/uv:0.13.6-python3.12-bookworm-slim` does not exist, so the build stage is now `python:3.12-slim-bookworm` with the pinned uv binary copied from `ghcr.io/astral-sh/uv:0.13.6` (uv's documented pattern). Compose ports are configurable (`WEB_PORT`, `API_PORT`) so the stack can run beside the dev servers.
- **D54. Re-warm after every data change.** The startup warm-up only ran when the database was already seeded, so on a first boot the cache was cold until the first visitor. Now any ingest that changes rows bumps the data version and re-warms the default view and the 24-cutoff sweep; the first request after boot takes about 20 ms.
- **D55. Vercel: one project, UI + API.** The brief allows Vercel or Heroku. One Vercel project serves the static UI and the FastAPI app as a Python function (`api/index.py`), with `/api/*` rewritten to it, so there is one URL and no CORS. Serverless constraints shape the settings it sets: SQLite in `/tmp` seeded from the bundled raw cache on each cold start (`SEED_BLOCKING=true`, because a background seed would freeze between requests), no background warm-up (`WARM_CACHE=false`), and a random admin token unless `ADMIN_TOKEN` is set. Simulated locally from a clean venv with only `requirements.txt` (106 MB of deps, under the 500 MB limit): ready in 2.8 s, same MAE/bias/skill, 401 on unauthenticated refresh, raw cache untouched. Relies on Vercel's FastAPI lifespan support (December 2025). Live check: every API route returns 200 in 0.25–0.55 s (xlsx 1.4 s), the summary matches local exactly, CSV has 1,488 rows, the UI uses the live API (footer `API 0.1.0 (992e418)`, no snapshot banner), deep links work and assets are immutable. On a fresh instance the 24-cutoff sweep takes a few seconds once, then about 0.3 s.
